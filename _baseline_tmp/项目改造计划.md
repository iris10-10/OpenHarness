## 一、项目概述

### 1.1 改造背景

OpenHarness 是一个生产级 Agent Harness，提供 Agent loop、tools/skills/plugins、memory、permissions、multi-agent coordination 等成熟基础设施。本项目基于 OpenHarness 进行定向改造，打造一款面向计算机行业求职者的全流程智能 Agent。

### 1.2 改造原则

| 原则 | 说明 |
|------|------|
| **最小侵入** | 最大化复用现有架构，核心引擎（Agent Loop、工具注册、权限检查等）不做破坏性修改 |
| **分层扩展** | 仅在知识层（RAG）、工具层（求职专用工具）、提示词层（领域上下文）三个层面扩展 |
| **渐进交付** | 按阶段迭代，每阶段可独立运行验证，降低集成风险 |
| **本地优先** | 敏感数据（简历、投递记录）本地存储优先，减少外部依赖和隐私风险 |

### 1.3 核心能力清单

改造完成后，求职 Agent 将具备以下能力：

- **简历管理**: 解析、生成、优化、多版本对比
- **岗位匹配**: 语义相似度匹配、技能差距分析
- **面试准备**: 题目生成、模拟面试、答案评分
- **薪资调研**: 多维度薪资查询、对比、谈判策略
- **公司背调**: 公司信息、技术栈、文化、面试评价
- **投递追踪**: 全生命周期投递记录与状态管理
- **知识检索**: RAG 驱动的岗位/面经/题库语义搜索
- **Web 仪表盘**: 可视化求职进度、数据看板、交互界面

### 5.4 详细功能说明

#### 5.4.1 向量数据库 (vectorstore.py)

**核心能力**:
- ChromaDB 本地持久化存储，数据目录：`~/.openharness/chromadb/`
- 预定义 5 个 Collection：`jobs`、`resumes`、`interview`、`companies`、`knowledge`
- 支持增删改查 CRUD 操作
- 支持元数据过滤（按公司、岗位类型、城市、日期等）
- 提供降级方案：FAISS 离线索引（当 ChromaDB 不可用时）

**Collection Schema**:
```python
# jobs collection
{
    "id": str,
    "document": str,           # 完整 JD 文本
    "embedding": List[float],
    "metadata": {
        "company": str,
        "title": str,
        "city": str,
        "salary_min": int,
        "salary_max": int,
        "experience": str,
        "education": str,
        "tags": List[str],     # 技能标签
        "source": str,         # 数据来源
        "posted_date": str,
        "url": str
    }
}
```

#### 5.4.2 Embedding 服务 (embedding.py)

**核心能力**:
- 多 Provider 策略：在线 API 优先，本地模型兜底
- 自动降级：在线服务不可用时自动切换到本地模型
- 结果缓存：基于内容哈希的缓存，避免重复计算
- 批量处理：支持批量文本向量化，提高效率

**配置项**:
```python
rag:
  embedding:
    provider: "auto"           # auto / openai / local
    openai_model: "text-embedding-3-small"
    local_model: "BAAI/bge-m3"
    cache_enabled: true
    cache_ttl_days: 30
```

#### 5.4.3 文档摄入管道 (ingestion.py)

**核心能力**:
- 多格式支持：PDF、Markdown、JSON、HTML、纯文本
- 智能分块：按语义段落切分，保持上下文完整性
  - 固定大小分块（默认 512 tokens，重叠 64 tokens）
  - 语义分块（基于段落/标题边界）
- 元数据自动提取：来源、类型、日期、关键词
- 增量更新：基于文件哈希判断，仅处理新增/变更文档
- 批处理：支持目录批量导入

**分块策略**:
1. 预处理：去除冗余空白、标准化格式
2. 粗分：按标题/段落边界切分
3. 细分：超过 max_tokens 的块继续切分，保留重叠
4. 元数据注入：每个 chunk 携带完整元数据

#### 5.4.4 检索排序器 (retriever.py)

**两阶段检索**:
- **阶段一 · 召回**: 向量相似度 + BM25 关键词混合检索，返回 Top-K（默认 20）
- **阶段二 · 精排**: 基于 LLM 的相关性评分，结合元数据权重，返回 Top-N（默认 5）

**混合检索策略**:
```
score = α * vector_score + (1-α) * bm25_score
其中 α 默认 0.7，可配置
```

**上下文窗口控制**:
- 检索结果总 token 数不超过预算（默认上下文的 25%）
- 按相关性从高到低填充，超出部分截断
- 提供摘要模式：长文档先摘要再注入

#### 5.4.5 RAG 检索工具 (rag_search_tool.py)

**工具列表**:
| 工具名 | 功能 | 输入 | 输出 |
|--------|------|------|------|
| `rag_search` | 通用语义搜索 | query, collection(可选), top_k(可选) | 相关文档列表 |
| `rag_search_jobs` | 岗位搜索 | query, filters(城市/薪资/经验等) | 匹配岗位列表 |
| `rag_search_interview` | 面经搜索 | query, company(可选), position(可选) | 相关面经题目 |

**权限**: RAG 工具均标记为 read-only，默认允许执行。

#### 5.4.6 RAG 上下文注入

**注入位置**: `build_runtime_system_prompt()` 中。该函数内部按条件动态组装 `sections` 列表（段数不固定，随 fast_mode、Issue/PR/Repo 上下文、项目记忆等条件增减），求职扩展在 `sections` 末尾追加 3 段：
- RAG 检索结果（根据当前 query 自动检索）
- 用户求职画像摘要（从 user_profile 读取）
- 当前投递状态概览（从 application_tracker 读取）

**Token 预算**:
- RAG 相关内容总 token ≤ 上下文窗口的 25%
- 与现有 compact 压缩机制协同，超限时优先压缩 RAG 内容

#### 9.4.3 权限策略调整

现有 `PermissionChecker` **不存在自定义“权限类别”体系**（read-only / file_write / network 三级分类为初稿设想，实际代码中无此机制）。真实权限模型为：`permission.mode`（DEFAULT / PLAN / FULL_AUTO）+ `allowed_tools` / `denied_tools` 工具白黑名单 + `path_rules` 路径规则 + `denied_commands` 命令黑名单，加上每个工具自身的 `is_read_only()` 布尔值——DEFAULT 模式下只读工具直接执行、变更类工具需用户批准。求职工具的权限策略**完全在现有模型内实现，不修改 `permissions/checker.py`**：

| 工具类别 | 实现机制 | 默认行为 | 说明 |
|---------|---------|---------|------|
| RAG 检索 / 岗位匹配 / 面试 / 薪资调研 | 工具类覆写 `is_read_only()` 返回 `True` | 允许 | DEFAULT 模式下只读工具直接执行，不弹审批 |
| 简历工具 / 用户画像 / 投递追踪 | 保持默认 `is_read_only() = False` | DEFAULT 模式下需用户批准；常用工具可在 `permission` 配置的 `allowed_tools` 白名单中放行 | 写入本地文件，属变更类操作 |
| 爬虫工具 / 公司背调 | 保持默认；公司背调直接复用现有 `web_search` / `web_fetch` 工具 | DEFAULT 模式下需用户确认 | 网络请求走现有审批对话框，无需新增机制 |

## 十二、风险与应对措施

### 12.1 技术风险

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|---------|
| ChromaDB 在大数据量下性能下降 | 检索变慢 | 中 | 提前做性能测试，预留 Qdrant 作为备选；合理设置 collection 分区 |
| 本地 Embedding 模型内存占用高 | 低配机器无法运行 | 中 | 提供小模型选项（all-MiniLM），默认使用在线 API，本地模型为可选 |
| RAG 检索质量不达预期 | 回答不准确 | 中 | 优化分块策略、增加重排序、引入查询改写、持续迭代 |
| 爬虫反爬升级导致采集失败 | 数据源中断 | 高 | 爬虫仅作为补充，核心数据依赖本地导入；提供 API 接入方式 |
| Web UI 与 CLI 功能不一致 | 用户体验割裂 | 中 | 统一调用后端 API 层，CLI 和 Web UI 共享同一套业务逻辑 |

### 12.2 合规风险

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 爬虫数据合规性 | 法律风险 | 遵守 robots.txt，仅采集公开信息，提供开关默认关闭，用户自行承担风险 |
| 简历隐私数据泄露 | 安全风险 | 本地优先存储，敏感字段脱敏，不将隐私数据发送到外部 API（可选本地 Embedding） |
| 求职建议免责 | 误导风险 | 明确声明"仅供参考，不构成求职决策依据"，鼓励多方验证 |

### 12.3 项目风险

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 工作量超出预期 | 延期 | 按优先级迭代，P0 功能先交付，P1/P2 可延后 |
| 代码质量下降 | 维护困难 | 严格遵循开发规范，Code Review，单元测试覆盖 |
| 与上游 OpenHarness 升级冲突 | 合并困难 | 最小侵入原则，新增代码独立成模块，尽量不修改核心代码 |
