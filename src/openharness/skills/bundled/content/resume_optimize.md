# 简历优化技能

以 STAR 法则重写项目经历、注入目标岗位关键词、量化成果，系统性提升简历质量与 ATS（简历筛选系统）匹配度。

## 何时使用

- 用户要求优化简历、改简历、点评简历、提升 ATS 匹配度
- 用户要改写项目经历 / 工作经历，让表述更专业
- 用户拿着一份 JD，问"简历怎么针对这个岗位调整"
- 用户简历投出后没有面试邀约，需要诊断原因

## 优化流程

1. **拿到材料**：请用户提供简历文本或文件（.md / .txt）。有目标岗位时同时要 JD；没有 JD 就先问目标岗位方向。
2. **分析当前问题**：调用 `resume_parse` 解析结构并获取 ATS 评分；有 JD 时调用 `jd_parse` 提取岗位要求，再用 `resume_optimize`（或 `job_match`）做关键词对齐分析。明确列出问题清单（如：经历流水账、无量化、关键词缺失、排版混乱）。
3. **STAR 法则重写项目经历**：按下方"STAR 法则要点"逐条改写，突出 Action 与 Result。
4. **注入目标岗位关键词**：从 JD 的必备/加分技能中挑出用户真实具备但简历未体现的词，自然融入技能栏与项目描述。用户不具备的技能**不得**写入（不造假）。
5. **量化成果**：为每段主要经历补上数字（性能、规模、收益），数字必须来自用户口述或原始简历，缺失时先向用户求证。
6. **输出优化前后对比**：给出"改写前 → 改写后"对照表与改动理由；再调用 `resume_parse` 复评 ATS 分数，展示提升幅度。需要生成完整版式时用 `resume_generate`，比较多版本时用 `resume_compare`。

## 输出要求

- 问题诊断 → 改写示例 → 关键词对照 → ATS 分数变化，分节呈现
- 每条建议标注"为什么这样改"（对应哪条筛选逻辑 / 哪个岗位要求）
- 保存草稿前告知用户文件位置；不代替用户投递

## 参考资料（内联于本文件；bundled 技能不支持 references/ 子目录）

### STAR 法则要点

四要素：

| 要素 | 含义 | 写作要点 | 常见错误 |
|------|------|---------|---------|
| **S**ituation | 项目背景 | 1 句话交代业务场景与约束（日活、数据量、团队规模） | 背景写半段，喧宾夺主 |
| **T**ask | 承担的任务 | 明确"我负责什么"，边界清晰 | 写成整个团队的产出，看不出个人贡献 |
| **A**ction | 采取的行动 | 技术选型理由、方案对比、关键实现，用动词开头（设计/重构/优化） | 罗列技术名词，没有决策过程 |
| **R**esult | 结果与收益 | 量化收尾 + 一句沉淀（方法论/复用） | 没有结果，或结果与 Action 无因果 |

改写模板：`在 [S 背景] 下，负责 [T 任务]。通过 [A 关键动作 1/2/3]，实现 [R 量化结果]，沉淀了 [R' 方法论/复用]。`

改写示例：

- 改写前：`参与订单系统开发，使用 Redis 缓存，性能得到提升。`
- 改写后：`在日订单量 50 万的电商系统中（S），负责订单查询链路的性能优化（T）。针对热点订单 90% 查询集中在最近 7 天的特征，设计本地缓存 + Redis 二级缓存方案并治理缓存击穿（A），订单详情接口 P99 从 480ms 降至 60ms，DB 读 QPS 下降 75%（R）。`

### ATS 关键词库（按岗位方向）

ATS 常见筛选维度：**职位标题精确匹配 > 技能关键词 > 学历/年限 > 认证**。关键词尽量同时出现在"技能栏"与"项目经历"中（出现 2 次以上权重更高）。

- **后端**：Java / Go / Python / C++、Spring Boot / Gin / Django、MySQL、Redis、Kafka / RabbitMQ、微服务、分布式、高并发、高可用、分库分表、服务治理、Kubernetes、Docker、性能调优、链路追踪
- **前端**：JavaScript / TypeScript、React / Vue、Next.js、Webpack / Vite、Node.js、SSR / CSR、性能优化（FCP/LCP）、跨端（小程序 / Hybrid）、低代码、可视化（ECharts / D3）、微前端、无障碍
- **算法 / 机器学习**：PyTorch / TensorFlow、推荐系统、NLP / CV / LLM、大模型微调（SFT / LoRA）、RAG、特征工程、A/B 测试、召回 / 排序、分布式训练、模型部署与推理优化
- **数据**：SQL、Hive / Spark / Flink、数仓建模（维度建模 / 分层）、ETL、ClickHouse / Doris、Tableau / Superset、指标体系、归因分析、用户画像
- **测试**：自动化测试（Pytest / JUnit / Playwright）、接口测试、性能测试（JMeter / Locust）、测试平台开发、CI/CD、质量体系、混沌工程
- **运维 / SRE**：Linux、Kubernetes、Prometheus / Grafana、Terraform / Ansible、CI/CD（Jenkins / GitLab CI）、日志体系（ELK）、故障排查、成本优化、稳定性（SLA / SLO）

岗位匹配提示：对照 JD 的"任职要求"逐条核对，必备技能（前 3-5 个关键词）必须在简历前 1/3 出现。

### 成果量化句式库

- **性能**：接口耗时 P99 从 X 降至 Y；QPS 提升 N%；错误率从 X% 降到 Y%
- **规模**：支撑日活 X 万 / 峰值 QPS X / 数据量 X TB / 服务 X 个团队
- **收益**：年化节省成本 X 万；转化率提升 X 个百分点；人效提升 X%
- **质量**：线上事故数下降 X%；单测覆盖率从 X% 提升到 Y%；发布回滚率下降 X%
- **效率**：构建时间从 X 分钟降到 Y 分钟；需求交付周期缩短 X%
- **无法量化的经历**：写"影响面"（服务多少用户/多少业务方）或"复用性"（方案被 N 个团队复用）

### 简历常见问题清单（诊断用）

1. 工作内容流水账，只有职责没有成果（缺 R）
2. 全程"参与/协助"，看不出个人贡献（缺 A 的主语）
3. 技术名词堆砌，没有选型理由与权衡（缺 A 的过程）
4. 关键词与目标 JD 不匹配（ATS 过滤）
5. 项目过多且无重点（应保留 2-4 个与目标岗位最相关的）
6. 排版花哨（双栏/图表/图片文本，ATS 解析失败）、文件名随意（应为"姓名-岗位-年限.pdf"）
7. 一份简历投所有岗位（应按方向维护 2-3 个版本）

### 硬性规则

- **不造假**：不编造经历、技能、数字；所有量化数据须用户确认
- 优化是"表达增强"而非"事实虚构"——把用户做过的事写清楚，而不是写没做过的事
